# User Service

Регистрация, вход, профили, поиск пользователей, заявки, дружба и блокировки.

Стек: Go + Gin, PostgreSQL (pgx), bcrypt, JWT.

HTTP-контракт с примерами: [docs/contracts.md](docs/contracts.md).

## Реализовано

- `POST /users/{id}/friend-requests` — отправить заявку с обязательным `Idempotency-Key`. Повтор тем же ключом и получателем возвращает сохранённый результат в течение 24 часов; другой получатель — `409 IDEMPOTENCY_CONFLICT`. Новая попытка с новым ключом при существующей заявке возвращает `409` с её ID. Дружба появляется только после принятия.
- `GET /friend-requests?direction=incoming|outgoing` — свои ожидающие заявки с пагинацией.
- `POST /friend-requests/{id}/accept` — принять входящую заявку.
- `DELETE /friend-requests/{id}` — отменить исходящую или отклонить входящую заявку.
- `GET /users/{id}/friends` — список друзей по приватности профиля и раздела. Для собственного списка также можно использовать `/users/me/friends` с токеном.
- `DELETE /users/me/friends/{user_id}` — удалить взаимную дружбу. Счётчики профилей обновляются автоматически. Сохранённые блокировки в обе стороны запрещают отправку/принятие заявки и доступ уровня `friends`.
- `PUT /users/me/blocks/{user_id}` — заблокировать пользователя и атомарно отменить ожидающую заявку в любую сторону. Дружба сохраняется.
- `DELETE /users/me/blocks/{user_id}` — снять только собственную блокировку. Встречная блокировка продолжает действовать; отменённые заявки не восстанавливаются.
- `GET /users/me/blocks?limit=20&cursor=...` — собственные блокировки: публичные карточки пользователей, сортировка по имени без регистра и ID, страницы по 1–20 записей. Все три маршрута требуют действующей сессии, повторные PUT/DELETE дают `204`.

- `POST /auth/register` — регистрация по email, username, password и password_confirmation. Валидация данных, уникальность email и имени без учёта регистра, bcrypt-хеширование пароля. Ответ: `201` с `user_id`.
- `POST /auth/login` — вход по email или имени и паролю. Ответ: `access_token`, `refresh_token`, `expires_in`, `user`.
- `POST /auth/refresh` — обновление пары токенов с проверкой срока refresh и транзакционной ротацией. Старый refresh больше не действует.
- `GET /users/me` — собственные `id`, `email`, `username`, `avatar_url`, `banner_url`, `description`, `friends_count`, `privacy`. Требует `Authorization: Bearer <access_token>`. `avatar_url` и `banner_url` пока равны `null`: клиент показывает стандартные аватар и фон шапки профиля. Описание — строка либо `null`, число друзей — целое, включая `0`; владелец видит их независимо от приватности. Эти поля также возвращаются в `user` при входе.
- `GET /users/{id}` — просмотр профиля гостем или с Bearer-токеном. Возвращает публичные `id`, `username`, `avatar_url`, `banner_url` (изображения пока `null`), `is_private`; описание и число друзей выдаются только при разрешённом доступе к профилю и соответствующему разделу. Владелец видит эти данные независимо от приватности. Доступ `friends` требует дружбы и отсутствия блокировки в любую сторону. При закрытом профиле остаются публичные поля и `is_private=true`; email, роль и настройки приватности не раскрываются. Неверный переданный токен возвращает `401`, отозванная сессия — `401 SESSION_REVOKED`, отсутствующий профиль — `404 PROFILE_NOT_FOUND`. Списки сообществ и коллекций будут подключены через их сервисы отдельно.
- `GET /users?q=anna&limit=20&cursor=...` — публичный поиск по имени без авторизации. Запрос обязателен, минимум 2 символа после trim, регистр не учитывается. Сначала полное совпадение, затем начало имени, затем вхождение; внутри групп — имя без регистра и ID. Ответ: `items` с `id`, `username`, `avatar_url` (пока `null`) и `next_cursor` (либо `null`). Email и настройки приватности не выдаются. `limit` по умолчанию 20, допустимы 1–20; следующая страница использует тот же `q` и полученный курсор. Ошибки `400`: `QUERY_REQUIRED`, `QUERY_TOO_SHORT`, `INVALID_LIMIT`, `INVALID_CURSOR`.
- Проверка JWT и JSON-ответы об ошибках.
- Каждая прикладная ошибка содержит `request_id`, совпадающий с заголовком ответа `X-Request-ID`. Сервер генерирует новый ID для каждого запроса; заголовок есть и в успешных ответах.
- При сбое чтения профиля с проверкой приватности, дружбы и блокировок возвращается `503 SERVICE_UNAVAILABLE` без данных профиля. Отсутствующий профиль по-прежнему возвращает `404 PROFILE_NOT_FOUND`.
- Серверные сессии: отдельная на каждый вход, проверка при доступе к профилю и refresh. Refresh не продлевает исходный срок сессии.
- `POST /auth/logout` — `204`, отзыв только текущей сессии. После выхода её access и refresh возвращают `401 SESSION_REVOKED`; другие устройства продолжают работать.
- Истёкшая сессия возвращает `401 SESSION_EXPIRED`, недоступность проверки сессии — `503 SERVICE_UNAVAILABLE`.
- `privacy` создаётся вместе с аккаунтом и возвращается при входе и в `/users/me`.
- Пять последовательных неверных попыток блокируют вход по идентификатору на час: `429 LOGIN_LOCKED`, включая несуществующие аккаунты. Email и имя имеют независимые счётчики; регистр и пробелы по краям не различаются. Успешный вход сбрасывает счётчик; после окончания блокировки или часового перерыва следующая ошибка начинает новый отсчёт. Неверный формат возвращает `400 INVALID_LOGIN` без увеличения счётчика.

## Внутреннее API

- `POST /internal/auth/introspect` — проверка пользовательского access и сессии: `200 {"active":true,"user_id":"..."}` либо `200 {"active":false}`, без роли.
- `POST /internal/auth/permission-check` — только для Moderation: проверка `catalog_submissions.review`, ответ `{"allowed":true}` для администратора платформы или `{"allowed":false}` для обычного пользователя с действующей сессией.
- `POST /internal/users/access-check` — пакетная проверка приватности, дружбы и блокировок для Collection/Community.
- `POST /internal/users/previews` — публичные карточки пачкой.
- `GET /internal/users/{id}/blocked-user-ids` — исходящие блокировки текущего пользователя, только для Community.

Служебные секреты задаются JSON-картой `INTERNAL_SERVICE_TOKENS`, пример в `.env.example`. Без неё внутреннее API отвечает `503`; публичное продолжает работать. Секреты минимум 32 байта, разные для сервисов. Служебный секрет передаётся как Bearer; пользовательский access — отдельно по контракту. При развёртывании внутренние маршруты закрываются от внешнего Gateway, вызовы выполняются по TLS. Примеры запросов и права сервисов — в разделе 11 контракта. Сообщения исключены из MVP, API для Messaging не добавляется.

## Проверки работоспособности

- `GET /health` → `200 {"status":"ok"}`: HTTP-сервис отвечает, независимо от PostgreSQL.
- `GET /ready` → `200 {"status":"ready"}`, если PostgreSQL отвечает на Ping; иначе `503 SERVICE_UNAVAILABLE`. Таймаут проверки — 2 секунды.

Токены не требуются. При недоступности обязательной проверки блокировки входа возвращается `503`. Повтор собственной отмены/отказа по заявке даёт `204`, попытка обработать заявку, уже закрытую другим участником, — `409 FRIEND_REQUEST_NOT_PENDING`.

## Создание таблиц

Для новой БД выполни `migrations/000001_init.sql`: он создаёт аккаунты, сессии, refresh-токены, приватность, счётчики входа, заявки в друзья, дружбу, блокировки и индексы. Также создаётся `idempotency_keys` для сохранения результатов отправки заявок. Для уже созданной БД повторно выполни обновлённый init: новая таблица добавится без удаления данных; down выполнять не нужно. `000002_down.sql` удаляет таблицы; при обычном запуске его не выполняют. `CREATE TABLE IF NOT EXISTS` не обновляет структуру существующих таблиц.
