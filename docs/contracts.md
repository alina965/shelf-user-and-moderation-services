# User Service: HTTP-контракт

Актуализировано 20 ноября 2026 года по маршрутам, DTO и обработчикам сервиса. Разделы 1–10 описывают реализованное поведение. Раздел 11 содержит границы интеграции и ещё не реализованные внутренние методы.

## 1. Адреса и общие правила

- Прямой локальный адрес: `http://localhost:8080`. Порт и интерфейс задаются переменной `ADDR`.
- В примерах пути указаны относительно прямого адреса сервиса, **без `/api/v1`**. Этот префикс предусмотрен архитектурой для Gateway, но сам сервис его не регистрирует. Адрес Gateway и правила удаления префикса нужно согласовать при развёртывании.
- Для стандартного Android Emulator адрес сервиса на компьютере: `http://10.0.2.2:8080`, если сервис слушает доступный интерфейс. На физическом телефоне `localhost` означает сам телефон.
- В Docker другой контейнер использует сетевое имя контейнера/сервиса и его порт, а не свой `localhost`. Имя и сеть определяются конфигурацией развёртывания.
- Тела POST-запросов: JSON UTF-8, заголовок `Content-Type: application/json`. У logout тела нет.
- ID передаются строками UUID. Клиент хранит ID как непрозрачную строку, не строит его из username.
- Успешные ответы с данными имеют JSON-тело. `204` не имеет тела: вызывать JSON-декодер для него не нужно.
- Каждый запрос получает сгенерированный сервером ID в заголовке ответа `X-Request-ID`, включая успешные ответы и `204`. В прикладных JSON-ошибках тот же ID передаётся в `request_id`. Входящий `X-Request-ID` не используется: сервер создаёт собственный ID.
- В GET-запросах используются query-параметры, тело не требуется. Значения параметров нужно URL-кодировать средствами HTTP-клиента.
- Пароли и токены нельзя помещать в URL.
- Наличие поля в схеме БД не означает наличие поля в HTTP-ответе. В частности, `role`, ключи изображений и хеш пароля сейчас не выдаются.

Реализованные операции:

1. `POST /auth/register` — регистрация.
2. `POST /auth/login` — вход.
3. `POST /auth/refresh` — ротация токенов.
4. `POST /auth/logout` — выход из текущей сессии.
5. `GET /users/me` — собственные данные и privacy.
6. `GET /users` — публичный поиск пользователей.
7. `GET /users/{id}` — профиль с учётом прав зрителя.

## 2. Авторизация и время жизни

Защищённые запросы передают:

```http
Authorization: Bearer <access_token>
```

Сервер проверяет подпись и срок access-токена, затем существование, владельца, срок и отзыв серверной сессии. Каждый успешный вход создаёт отдельную сессию. Выход на одном устройстве не завершает другие сессии.

Срок access задаёт `ACCESS_TOKEN_TTL`, срок сессии и refresh — `REFRESH_TOKEN_TTL`. Если переменные отсутствуют или не разбираются, текущие значения по умолчанию: access — 1 минута, сессия — 7 дней. В `.env.example` предлагаются `15m` и `720h` соответственно. Клиент использует возвращённый `expires_in`, а не фиксированное число из примеров.

`expires_in` — целое число секунд до истечения access на момент ответа. Из-за времени обработки ответ может содержать, например, `899` вместо `900`. Отдельные `expires_at`, `token_type` и срок refresh в текущих ответах отсутствуют.

Refresh не продлевает исходный срок сессии. После его окончания требуется вход с паролем. Отзыв сессии запрещает дальнейшие защищённые запросы и обновление её действующего refresh. Уже выполняющийся запрос сам по себе не отменяется.

## 3. Регистрация: `POST /auth/register`

Авторизация не требуется. Принимаются четыре обязательных поля:

```http
POST /auth/register
Content-Type: application/json

{
  "email": "anna@example.com",
  "username": "Anna",
  "password": "ExamplePass123!",
  "password_confirmation": "ExamplePass123!"
}
```

Текущая валидация:

- Email: пробелы по краям удаляются, проверяется формат, длина до 254 символов. Email уникален без учёта регистра.
- Username: пробелы по краям удаляются; 1–32 символа, латинские буквы, цифры, `_` и `.`. Точка не может быть первой/последней; две точки подряд запрещены. Имя уникально без учёта регистра, исходный регистр сохраняется для отображения.
- Пароль: 8–32 Unicode-символа и не более 72 байт UTF-8. Значение не обрезается и не изменяется. Подтверждение должно совпадать.
- Проверка списка зарезервированных имён пока отсутствует.
- Пользователь и его privacy создаются одной транзакцией. Все четыре настройки новой записи имеют значение `public`.

Ответ `201 Created`:

```json
{
  "user_id": "11111111-1111-4111-8111-111111111111"
}
```

**Регистрация не возвращает токены.** После неё нужно выполнить вход. Подтверждение почты и отправка письма сейчас не требуются и не выполняются.

Ошибки: `400 INVALID_JSON`, `400 INVALID_REGISTRATION`, `409 ACCOUNT_EXISTS`, `500 INTERNAL_ERROR`. Ответ регистрации не указывает отдельным полем, занят email или username.

## 4. Вход: `POST /auth/login`

Авторизация не требуется. `identifier` содержит email **или** username:

```http
POST /auth/login
Content-Type: application/json

{
  "identifier": "anna@example.com",
  "password": "ExamplePass123!"
}
```

Можно передать `"identifier": "Anna"`. Пробелы по краям идентификатора удаляются, регистр при поиске и учёте ошибок не различается. Пароль не изменяется.

Ответ `200 OK`:

```json
{
  "access_token": "<access_token>",
  "refresh_token": "<refresh_token>",
  "expires_in": 899,
  "user": {
    "id": "11111111-1111-4111-8111-111111111111",
    "email": "anna@example.com",
    "username": "Anna",
    "avatar_url": null,
    "banner_url": null,
    "description": null,
    "friends_count": 0,
    "privacy": {
      "profile_visibility": "public",
      "description_visibility": "public",
      "friends_visibility": "public",
      "communities_visibility": "public"
    }
  }
}
```

Блокировка входа:

- Ошибки формата возвращают `400 INVALID_LOGIN` и не увеличивают счётчик. Пустой пароль и пароль длиннее 32 символов относятся к этим ошибкам. Минимальная длина при входе не проверяется: непустой короткий пароль считается неверными учётными данными.
- Первые четыре последовательные ошибки учётных данных возвращают `401 BAD_CREDENTIALS`.
- Пятая ошибка возвращает `429 LOGIN_LOCKED` и блокирует идентификатор на час.
- Во время блокировки даже правильный пароль возвращает `429 LOGIN_LOCKED`. Запросы не продлевают блокировку.
- Несуществующий корректно записанный идентификатор учитывается по тем же правилам; ошибки не раскрывают наличие аккаунта.
- Email и username одного пользователя имеют независимые счётчики.
- Успешный вход сбрасывает счётчик использованного идентификатора. После окончания блокировки или часа с последней ошибки следующая неудачная попытка начинает новый отсчёт.
- Сброс при успешном входе выполняется в одной транзакции с созданием сессии и сохранением refresh.
- Письма о блокировке пока не отправляются. Полей `retry_after`, `locked_until` и заголовка `Retry-After` в контракте сейчас нет.

Ошибки: `400 INVALID_JSON`, `400 INVALID_LOGIN`, `401 BAD_CREDENTIALS`, `429 LOGIN_LOCKED`, `503 SERVICE_UNAVAILABLE` при сбое загрузки профиля/проверки доступа, `500 INTERNAL_ERROR` для других внутренних ошибок.

## 5. Обновление токенов: `POST /auth/refresh`

Access-токен не требуется. Право на обновление подтверждается refresh в теле:

```http
POST /auth/refresh
Content-Type: application/json

{
  "refresh_token": "<current_refresh_token>"
}
```

Ответ `200 OK`:

```json
{
  "access_token": "<new_access_token>",
  "refresh_token": "<new_refresh_token>",
  "expires_in": 899
}
```

Сервер проверяет refresh и связанную сессию. Старый refresh удаляется, новый сохраняется транзакционно в той же сессии с исходным сроком окончания. Повтор использованного refresh возвращает `401 INVALID_REFRESH_TOKEN`. Не нужно ожидать, что старый access обязательно изменится строково: при выпуске в ту же секунду JWT может совпасть.

Клиент сохраняет **оба** токена из успешного ответа. Одновременные refresh-запросы одной пары нужно объединять: первый может пройти, остальные получат ошибку старого refresh. Если ответ потерян после успешной ротации, повтор старого refresh не гарантирует успех; восстановления потерянной новой пары по старому токену сейчас нет.

Ошибки:

- `400 INVALID_JSON` — тело не удалось прочитать как ожидаемый JSON.
- `401 INVALID_REFRESH_TOKEN` — пустой, неизвестный, уже использованный или недействительный refresh.
- `401 SESSION_REVOKED` — найденный refresh принадлежит отозванной/отсутствующей сессии.
- `401 SESSION_EXPIRED` — найдена сессия, но её срок истёк.
- `503 SERVICE_UNAVAILABLE` — не удалось выполнить проверку сессии.
- `500 INTERNAL_ERROR` — другая внутренняя ошибка.

Для уже использованного refresh сервер может ответить `INVALID_REFRESH_TOKEN`, даже если его бывшая сессия позднее была отозвана: запись старого refresh уже удалена.

## 6. Выход: `POST /auth/logout`

Требует действующий access-токен и действующую серверную сессию:

```http
POST /auth/logout
Authorization: Bearer <access_token>
```

Тело отсутствует. Ответ: `204 No Content`, без JSON.

После подтверждённого выхода клиент удаляет локальные токены. Последующие запросы с ещё не истёкшим access этой сессии и обновление её действующего refresh возвращают `401 SESSION_REVOKED`. Другие сессии пользователя продолжают работать.

Повторный logout с отозванной сессией возвращает `401 SESSION_REVOKED`, а не повторный `204`. Если access уже истёк или не проходит проверку JWT, сначала вернётся `401 UNAUTHORIZED`.

Ошибки: `401 UNAUTHORIZED`, `401 SESSION_REVOKED`, `401 SESSION_EXPIRED`, `503 SERVICE_UNAVAILABLE`, `500 INTERNAL_ERROR`.

## 7. Собственный профиль: `GET /users/me`

Требует действующий access и серверную сессию:

```http
GET /users/me
Authorization: Bearer <access_token>
```

Ответ `200 OK`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "email": "anna@example.com",
  "username": "Anna",
  "avatar_url": null,
  "banner_url": null,
  "description": null,
  "friends_count": 0,
  "privacy": {
    "profile_visibility": "public",
    "description_visibility": "public",
    "friends_visibility": "public",
    "communities_visibility": "public"
  }
}
```

Это тот же DTO, что `user` в ответе входа. `avatar_url` и `banner_url` присутствуют и пока равны `null`: фронтенд показывает стандартный аватар и фон шапки профиля из ресурсов приложения. Загрузка изображений и выдача ссылок на файлы пока не реализованы. `description` присутствует всегда: строка либо `null`, если описание не задано. `friends_count` присутствует всегда как целое число, включая `0`. Владелец получает описание и число друзей независимо от приватности. В отличие от публичного профиля, собственный DTO содержит email и privacy, не содержит `is_private` и не скрывает эти два поля. Не следует использовать один обязательный DTO для обоих ответов.

Значения privacy: `public`, `friends`, `private`. Это сохранённые настройки владельца, а не ограничение его доступа к собственным данным. Публичного API изменения этих настроек пока нет.

Ошибки: `401 UNAUTHORIZED`, `401 SESSION_REVOKED`, `401 SESSION_EXPIRED`, `503 SERVICE_UNAVAILABLE`, `500 INTERNAL_ERROR`.

## 8. Поиск: `GET /users`

Публичный метод. Авторизация не нужна; этот маршрут не проверяет переданный Bearer-токен и не использует его для изменения выдачи.

Параметры:

- `q`: обязательная строка; пробелы по краям удаляются, минимум 2 символа, регистр не учитывается. Поиск только по username, не по email или описанию.
- `limit`: необязательное целое число от 1 до 20, по умолчанию 20.
- `cursor`: необязательная непрозрачная строка из `next_cursor` предыдущего ответа.

```http
GET /users?q=anna&limit=2
```

Ответ `200 OK`, пример:

```json
{
  "items": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "username": "Anna",
      "avatar_url": null
    },
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "username": "anna_books",
      "avatar_url": null
    }
  ],
  "next_cursor": "<opaque_cursor>"
}
```

Порядок: полное совпадение → начало имени → вхождение в другой позиции. Внутри каждой группы — имя без регистра, затем ID. `_`, `%` и обратная косая черта в запросе интерпретируются буквально, не как шаблон поиска.

Продолжение:

```http
GET /users?q=anna&limit=2&cursor=<opaque_cursor>
```

Курсор связан с нормализованным `q`. При смене запроса нужно сбросить курсор и начинать с первой страницы. Не следует разбирать или самостоятельно собирать курсор. Параметров `page` и `offset` нет. Клиент отбрасывает запоздавшие ответы предыдущего поискового запроса.

Пагинация использует последнюю позицию сортировки. Это не снимок всей базы: параллельные изменения пользователей могут влиять на следующие страницы.

Если совпадений нет:

```json
{
  "items": [],
  "next_cursor": null
}
```

На последней странице `next_cursor` равен `null`; число результатов может быть меньше `limit`. Общего `total` нет. Публичные имена закрытых профилей доступны в поиске, но поиск не даёт доступ к закрытым данным.

Ошибки: `400 QUERY_REQUIRED`, `400 QUERY_TOO_SHORT`, `400 INVALID_LIMIT`, `400 INVALID_CURSOR`, `500 INTERNAL_ERROR`.

## 9. Профиль по ID: `GET /users/{id}`

Доступен гостю. Чтобы учитывать дружбу или права владельца, передай действующий Bearer-токен. Если заголовок `Authorization` передан, сервер проверяет его и сессию: ошибочный/просроченный токен не превращает запрос автоматически в гостевой.

```http
GET /users/11111111-1111-4111-8111-111111111111
Authorization: Bearer <viewer_access_token>
```

Для гостевого запроса полностью убери заголовок `Authorization`. `viewer_id`, `user_id`, роль или другие поля от клиента не используются как доказательство личности зрителя.

Пример доступного профиля — `200 OK`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "username": "Anna",
  "avatar_url": null,
  "banner_url": null,
  "is_private": false,
  "description": "Люблю книги и кино",
  "friends_count": 0
}
```

Поля и ограничения:

- `id`, `username`, `avatar_url`, `banner_url`, `is_private` присутствуют всегда при `200`. Изображения пока всегда `null`; выдача файлов и загрузка изображений не реализованы.
- `is_private` означает, что **этому зрителю** закрыт профиль целиком. Это не сырое значение настройки: владелец или допущенный друг может получить `false`, даже если сохранённый профиль не `public`.
- `description` выдаётся только при доступе к профилю и описанию. При отсутствии значения в БД или запрете доступа поле отсутствует; при сохранённой пустой строке может прийти `""`.
- `friends_count` выдаётся только при доступе к профилю и списку друзей. Разрешённый нулевой счётчик — `0`. При запрете поле отсутствует; его отсутствие нельзя показывать как «0 друзей».
- Email, password/hash, role, privacy, ключи файлов и идентификатор сессии не выдаются, в том числе владельцу через этот маршрут. Для собственных email и privacy используй `/users/me`.
- Списков друзей, сообществ, коллекций и их дополнительных счётчиков в этом ответе пока нет.

Правила доступа:

1. Владелец с проверенной сессией видит доступные здесь собственные поля независимо от privacy.
2. `public` доступно всем.
3. `friends` доступно другу только при отсутствии блокировки в любую сторону.
4. `private` доступно только владельцу.
5. Сначала проверяется профиль целиком, затем отдельные поля/разделы. Блокировка не скрывает публичные данные и не удаляет саму дружбу.

Пример закрытого профиля — также `200 OK`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "username": "Anna",
  "avatar_url": null,
  "banner_url": null,
  "is_private": true
}
```

Изменённые права применяются при следующем запросе. Маршрут устанавливает `Cache-Control: no-store`. Проверка профиля, friendship и блокировок использует один SQL-запрос; отсутствие HTTP API управления дружбой пока не мешает учитывать уже сохранённые связи.

Ошибки: `404 PROFILE_NOT_FOUND` для неизвестного пользователя, некорректного UUID или нулевого UUID; `503 SERVICE_UNAVAILABLE` при сбое загрузки профиля с проверкой приватности, дружбы и блокировок, в том числе для гостя. При переданной авторизации также возможны `401 UNAUTHORIZED`, `401 SESSION_REVOKED`, `401 SESSION_EXPIRED` и `503 SERVICE_UNAVAILABLE` при недоступности проверки сессии. Закрытые данные при сбое не возвращаются. Другие внутренние ошибки — `500 INTERNAL_ERROR`.

## 10. Ошибки и поведение фронтенда

Общий формат ошибок, которые обрабатывает прикладной код:

```json
{
  "error": {
    "code": "LOGIN_LOCKED",
    "message": "Вход по этому идентификатору заблокирован на 1 час"
  },
  "request_id": "req_11111111-1111-4111-8111-111111111111"
}
```

Клиент принимает решения по HTTP-статусу и `error.code`. Текст `message` — пользовательское сообщение, не стабильный идентификатор. `request_id` совпадает с заголовком ответа `X-Request-ID`; его можно передавать при сообщении об ошибке. Формат сейчас — `req_` и UUID, но клиенту следует хранить его как непрозрачную строку. Список ошибок по полям и дополнительные `details` сейчас не возвращаются.

Справочник кодов:

- `400 INVALID_JSON` — JSON не удалось разобрать в структуру запроса.
- `400 INVALID_REGISTRATION` — не выполнены правила регистрации.
- `400 INVALID_LOGIN` — некорректно заполнены поля входа.
- `400 QUERY_REQUIRED` — не указан поисковый запрос или он пуст после trim.
- `400 QUERY_TOO_SHORT` — поисковый запрос короче двух символов.
- `400 INVALID_LIMIT` — limit не целое число в диапазоне 1–20.
- `400 INVALID_CURSOR` — курсор невалиден или относится к другому запросу.
- `401 BAD_CREDENTIALS` — неизвестный аккаунт или неверный пароль.
- `401 UNAUTHORIZED` — нет обязательного access, неверный формат Bearer, невалидный или истёкший JWT; также собственный пользователь больше не найден.
- `401 INVALID_REFRESH_TOKEN` — refresh не подходит для обновления.
- `401 SESSION_REVOKED` — серверная сессия отозвана или отсутствует.
- `401 SESSION_EXPIRED` — срок серверной сессии истёк.
- `404 PROFILE_NOT_FOUND` — профиль не найден либо ID некорректен.
- `409 ACCOUNT_EXISTS` — занят email или username.
- `429 LOGIN_LOCKED` — действует часовая блокировка идентификатора.
- `503 SERVICE_UNAVAILABLE` — временно не удалось проверить сессию или загрузить профиль для проверки доступа.
- `500 INTERNAL_ERROR` — другая ошибка сервера.

Не каждая ошибка БД превращается в `503`: ошибки поиска, записи и некоторых отдельных чтений могут попасть в `500`. Сбой объединённого запроса профиля с проверкой прав возвращает `503`, отсутствие пользователя остаётся `404`. Неизвестные маршруты, неподходящие методы и аварийные ответы Gin не гарантируют приведённый JSON-формат; клиент должен выдерживать не-JSON ответ и сетевую ошибку. При прохождении через middleware заголовок `X-Request-ID` присутствует и в таких ответах.

Рекомендуемый сценарий клиента:

1. Зарегистрировать аккаунт; после `201` открыть вход.
2. После успешного входа сохранить пару токенов в защищённом хранилище устройства.
3. Использовать access для защищённых запросов и персонализированного просмотра профиля.
4. При истечении access выполнить один refresh, сохранить новую пару и повторить исходный запрос один раз. Не запускать бесконечные повторы любого `401`.
5. При `SESSION_REVOKED` или `SESSION_EXPIRED` очистить токены и открыть вход. При `INVALID_REFRESH_TOKEN` новая пара этим refresh не получается — нужен повторный вход, если актуальной пары уже нет.
6. При `LOGIN_LOCKED` показать временную блокировку и не повторять пароль автоматически.
7. При `503` или сетевой ошибке показать временную недоступность. Серверный logout подтверждён только после `204`. При пользовательском выходе клиент удаляет локальные токены и при отсутствии подтверждения сообщает, что сессию на сервере завершить не удалось; сама сессия может оставаться действующей до отзыва или истечения срока.
8. У публичного профиля различать отсутствие закрытых полей, `null` изображения и числовой `0`. Описание отображать обычным текстом.

Примеры выше показывают форму контракта. UUID, токены, курсоры и сроки иллюстративные; строки вида `<access_token>` нужно заменять реальными значениями из ответов.

## 11. Интеграция с другими backend-сервисами

### Что доступно сейчас

Другой backend может вызвать реализованные HTTP-методы по доступному сетевому адресу User Service. Для публичного имени/заглушки изображения доступны поиск и профиль по ID. Для запроса от имени пользователя нужно передать его исходный access в `Authorization`; нельзя заменить его непроверенным `viewer_id` или заголовком с ID.

`GET /users/me` с переданным пользовательским access сейчас позволяет получить проверенный User Service ID пользователя. Это существующий пользовательский маршрут, а не внутренний introspection-контракт: он возвращает email/privacy, не возвращает роль, не аутентифицирует вызывающий сервис и не отвечает на вопросы дружбы или возможности отправить сообщение. Не следует использовать его как постоянную замену будущего internal API.

Сервису-потребителю не нужно получать refresh пользователя, обновлять его токены или знать `JWT_SECRET`. Refresh принадлежит клиентской сессии. Разбор JWT без проверки его серверной сессии не обеспечивает отзыв после logout. Наличие `user_id` или действующего токена также не означает право на чужую коллекцию, сообщение или административную операцию.

Данные принадлежат User Service: другие сервисы не читают его таблицы напрямую, не делают межсервисные SQL JOIN и не записывают дружбу/блокировки в своей БД как источник истины.

### Запланировано, но НЕ реализовано

Следующие маршруты перечислены в архитектурном описании, однако сейчас их нет в роутере. У них ещё нет реализованного контракта request/response. На них нельзя рассчитывать при запуске интеграции:

- `POST /internal/auth/introspect` — проверка access и серверной сессии, выдача user_id и глобальных полномочий.
- `POST /internal/users/access-check` — пакетные проверки доступа к профилю/разделам с учётом дружбы и блокировок для Collection и Community.
- `POST /internal/users/messaging-check` — существование получателя и отсутствие блокировки в обоих направлениях для Messaging.
- `POST /internal/users/previews` — пакетная выдача публичных имён и аватаров без email и закрытых данных.
- `GET /internal/users/{id}/blocked-user-ids` — собственные исходящие блокировки зрителя для фильтра ленты Community.

Перед подключением этих методов нужно реализовать и согласовать DTO, служебную аутентификацию, права вызывающих сервисов, таймауты и ошибки. По архитектуре internal API не публикуется через внешний Gateway, служебный вызов аутентифицируется отдельным токеном по TLS в защищённой сети. Это требуемая будущая настройка, а не уже включённая защита.

Если обязательную проверку доступа/блокировок выполнить не удалось, сервис-потребитель не разрешает действие и не раскрывает закрытые данные. Публичный профиль не заменяет `messaging-check`: видимость имени не доказывает право отправить сообщение.

### Другие отсутствующие возможности

Пока нет HTTP API управления дружбой и блокировками, списков друзей/сообществ/коллекций, редактирования профиля и privacy, загрузки аватара/баннера, выдачи административной роли, управления остальными сессиями, подтверждения почты и восстановления пароля. Нет WebSocket, событий или отдельного API регистрации устройств.
